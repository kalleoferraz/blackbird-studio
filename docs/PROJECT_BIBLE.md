# Blackbird Script Studio — Project Bible

Sep 30, 2026 · @Kalleo · Updated Oct 22, 2026, 17:07 (Berlin)

## 1. Vision and users

Blackbird Script Studio is a hosted web app where an author writes, records and organizes a media project (an audiobook, textbook, film, series or podcast) in one place, with a DAW-style timeline for every segment and a provable, incremental history of the written text.

- **Primary user (today):** the owner, a former developer and project manager. The tool began as the owner's own way to produce a multi-character fiction audiobook with free, open-source tools; the possibility of supporting several kinds of media (textbook, audiobook, film, series, podcast) made it a tool for all of them.
- **Later users:** other authors and narrators, invited per media project, each with a role.
- **Core problem:** text, recordings, sound effects, music and translations live in scattered folders and tools, with no structure linking a line of text to its audio.
- **Product principle:** the text is the spine. Every clip, effect and translation attaches to a stable cue of the story.

## 2. v1 scope and not-now list

v1 delivers login, media projects, a text editor with structure, a basic multi-lane timeline, a file library and saved versions. Everything else waits. The views of the MVP are described in section 13.

**In v1**

- **Accounts and teams:** login. The admin creates users and manages teams; a user belongs to zero, one or several teams (a user in no team is standalone). Any non-admin user can create a media project and becomes one of its authors. Authors assign members and roles per media project (v1 builds only the author role; every other role is treated as a viewer, see Membership rules), finding users by name or email among those who share a team with them. The admin is never a member and sees only users and media project overviews.
- **Projects Collection:** the home screen, a list of the media projects the user is a member of, each with cover and overview (section 13).
- **Redaction View:** the media project is divided into chapters and segments. Each segment is divided into scenes (time boxes) and reads like a DAW timeline, where every lane is a logical organizer (a character, a kind of sound effect, a music line) and holds cues. Audio can be recorded in the browser or assigned from the library.
- **Timeline basics:** multiple lanes, draggable and resizable cues, clips with offset, length and gain, waveform display, play and seek, record into a cue. Fades and looping are stored on the clip but have no interface in v1. The timeline panel is shown only for audiobooks, podcasts, films and series; a textbook has none.
- **Characters and notes:** project-level characters (name, default colour, picture, description, files) that lanes can link to, and notes on any level with reply threads and reference flags.
- **Library:** per media project, a folder tree of files (audio, pictures, anything) on the server behind `BlobStore`, with an asset record per file (hash, no duplicates per media project). Audio is uploaded as a 24-bit WAV master; the server derives an MP3 playback copy beside it. Images with a longest side above 600 px get a reduced copy (longest side exactly 600 px). Lists, cards and previews use the lightweight copy; the original is shown only where the image is the subject (Project View, character profile) and on download. Audio download offers WAV and MP3 in a menu; an image download delivers the original. While a new file uploads and encodes, its cue shows a loading indicator.
- **Versions:** a manual "Save snapshot" action that commits the text to a private GitHub repo (in v1 only authors save snapshots), plus a "Changes not in a snapshot yet" indicator showing the time since the last snapshot. Text is saved to MySQL when the user leaves the text field.
- **One editor per media project:** a media project can be open in only one tab or device at a time. Opening it elsewhere closes the editor in the older one (see section 4).

**Not now**

- Translation view, integrated LLM, text-to-speech, speech-to-speech, audio compiler (see section 7).
- Google Drive as audio storage (see section 7). v1 stores files on the server.
- Appendixes (the media project model leaves room for them), video clips and a common library shared between media projects (see section 7).
- Automatic (timer-based) snapshots. Saving a snapshot is one function, so a timer can call it later.
- Effects, automation and crossfades on the timeline, and interface controls for fades and looping (the clip fields already exist).
- Live multi-user editing and websockets.
- Typed-versus-pasted tracking and an edit-event log for provenance.
- Publishing a media project's snapshot history (a public repo or a visibility setting; section 7).
- Roles other than author and viewer (voice actor, translator, reviewer): designed in section 5 and built later; in v1 every non-author is a viewer.
- The printable `Script.pdf` in the snapshot repo (section 7).
- Audio versioning as proof of authorship (only the text is proven).
- Separating test data from live data (see section 4).

## 3. Architecture principles

The database holds live working state, Git holds text snapshots, and server-side storage holds immutable audio, so no single store has to do everything.

1. **The timeline is a description, not audio.** A segment's lanes, cues and clips (starts, lengths, offsets, gain, fades, loops) reference audio by asset ID. Moving, resizing or trimming never touches the audio. All times and lengths are integer milliseconds. Live state is stored in relational tables; JSON files exist only in the snapshot repo (see section 6).
2. **Assets are immutable.** An asset is never updated: a new version is a new asset, and a new clip. Each asset has a stable ID and a hash of its audio, unique per media project. Deleting an asset under `storyline` happens only on the author's explicit confirmation and is permanent (see section 6), so past versions keep their manifest entry but the audio may be gone. The one exception to "a clip's asset never changes" is the Replace action (section 6): it creates a new asset and re-points the users of the old one in a single transaction.
3. **Stable cue IDs from day one.** Every cue keeps a permanent ID that survives text edits and moves. The cue holds the text, and clips, notes and translations attach to that ID. IDs are generated by the app (ULID, `CHAR(26)`), never by the database, because MySQL has no `RETURNING`.
4. **Database as live state, Git as snapshots.** Edits go to MySQL when the user leaves the text field. Git receives commits only when an author (later any editing role) presses "Save snapshot" (a later timer may call the same function).
5. **Storage behind adapters.** `BlobStore` (put, get, stat, move, delete) and `VersionStore` (snapshot, list, readAt) are interfaces. The first implementations are server disk (`LocalDiskBlobStore`) and GitHub. Google Drive is a later `BlobStore`, not an assumption.
6. **The client never sees credentials.** All storage and GitHub access is configured and performed by the backend, using one central account.

## 4. Stack and hosting

The app runs on GoDaddy Node.js Hosting (a beta app platform with a Preview app and a Published app, not cPanel hosting; per GoDaddy's help pages and the container layout seen in the spike), using Node 22 with managed MySQL.

**Verified by the spike (2026-10-11 to 2026-10-13):** Node 22.23, deploy from GitHub, managed MySQL via `mysql2`, GitHub API commits through Octokit, and uploads up to 100 MiB per request. **Database spike (2026-10-15):** the host runs Percona Server 8.4.7 (MySQL 8.4 compatible, not MariaDB), default collation `utf8mb4_unicode_ci`, strict `sql_mode`, isolation `REPEATABLE-READ`, `lower_case_table_names = 0` (table names are case-sensitive, so all names stay lowercase) and `max_allowed_packet` 16 MiB. `CHECK` constraints are enforced; `JSON`, `SKIP LOCKED` and `GET_LOCK` work. **Triggers cannot be created** (binary logging is on and the user has no `SUPER`), so no rule may rely on one. **Image resizer (2026-10-16):** wasm-vips runs in a worker thread on the Preview host (Node 22.23.3, linux/x64, 16 CPUs reported). A generated 12 MP JPEG (4000×3000, 4.3 MB) took 0.89 s on the first call (0.21 s of it library load and worker start) and 0.18–0.19 s on the next four; a 3000×2000 PNG with transparency took 0.39 s; jsquash took 1.76 s on the same JPEG. The process peaked at 728 MB RSS (jsquash run included; 79 MB at start). Locally, wasm-vips passed 26 of 27 fixtures (orientations 1–8, alpha, Display P3 to sRGB, truncated and oversized files refused), 48 MP in 1.3 s at about 410 MB; the full report is `docs/spikes/image-resizer-report.md`. **Still unverified:** whether any file location is durable (see the disk findings below), websockets, scheduled jobs and backups.

**Two repos, two jobs.** The *code repo* deploys the app. The *snapshot repo* receives text versions at runtime. They must stay separate so snapshot commits never trigger a redeploy.

**Code layout.** A single package, not a monorepo: `src/server` (Fastify API), `src/web` (SPA, later) and `src/shared` (timeline types and the clip playback rule). ES modules with TypeScript `NodeNext` (imports in source carry the `.js` extension). `npm run build` compiles to `dist/`, and `npm start` runs `node dist/server/index.js`. **Observed on the host:** the Preview log shows the app started with `npm run dev` (`tsx watch src/server/index.ts`), not with build and start; whether Published does the same is unconfirmed. The port is read from the `PORT` environment variable. Spike routes (`/spike/*`) are token-guarded and are removed once the spike is done. The image code lives in `src/images` (inspection, EXIF orientation, a single-worker pool and the wasm-vips resizer).

**Migrations.** The host offers no SSH and no SQL access from its web interface, so migrations run from the app at startup, using Drizzle's programmatic migrator.

- The generated SQL files are committed to the repo and must reach the host (not git-ignored; the path must resolve under both `tsx` and `dist/`).
- The run is wrapped in a MySQL advisory lock (`GET_LOCK`), so Preview and Published booting together cannot apply the same migration twice. The lock is taken in `src/db/migrate.ts` (`GET_LOCK` with a 60 s wait, one dedicated connection) and the migrator runs inside it, so it does not matter whether Drizzle locks by itself. The app calls it from `src/server/index.ts` before listening, and skips it only when `DB_HOST` is unset (a local run without `.env`). The first migration is `drizzle/0000_init.sql`. MySQL DDL autocommits, so if that first run fails halfway the tables created so far stay and the migration is not recorded: drop those tables by hand before retrying.
- Migrations are **additive only** (new tables, nullable columns, indexes), with one recorded exception: `0019` (2026-10-21) swaps the `scene` and `segment` tables. Renames and drops happen in two steps, with the removal in a later publish. MySQL DDL is not transactional, so each migration is one small change (or safe to re-run).
- A failed migration stops startup, so the deploy is reported unhealthy.
- Preview and Published share one database (stated by GoDaddy's Hosted Database page): a migration applied by Preview is live for Published, and republishing older code runs it against the newer schema. Additive-only migrations are what keep the live app working in that gap.
- **Test and live data are mixed on purpose for now** (private single-owner tool). Test media projects should have a clear title, such as "TEST – …", so they are easy to find and delete. Revisit before public or multi-author use.

**Known limits to plan around**

- No SSH and no installable binaries (no ffmpeg on the server). MP3 encoding and image reduction use pure JS or WebAssembly code in a worker thread. Waveform peaks: see open questions.
- Outbound connections are limited to ports 80 and 443 and the managed MySQL; whether the managed MySQL accepts connections from outside is not documented, and the plan does not depend on it.
- Preview URLs require `?airoShareToken=...`; the Published URL does not (checked with curl, 2026-10-13).
- **Server disk (spike, 2026-10-13).** The app runs in a container whose root is read-only.
  - `/app` (including `public/assets`), `/local` (the home directory) and `/tmp` are on the node's local disk. Files there survived process restarts, source-only updates of Preview and a publish, but were **lost once** at an update whose cause is unknown (the one hypothesis, that a dependency change replaces the container, is not supported by the git history, which shows no dependency change in that window). Free space on that disk is the node's, not a quota, and shrinks as other tenants use it.
  - `/private` is a network (ceph) volume, writable, and **shared by Preview and Published**. Nothing else was visible in it. Its durability and quota are unverified: one marker written from Preview was visible from Published after a publish, and nothing more has been tested. The roughly 104 TB of free space it reports belongs to the volume, not to a quota for this app, and GoDaddy's help pages, as read in the spike, document no quotas or backups. **Working assumption: durable, until GoDaddy support answers.**
  - Preview and Published have separate local disks, but share MySQL (stated by GoDaddy's Hosted Database page) and `/private`. The hostname was identical in both environments on every request where it was captured, so it cannot tell instances apart; the per-process boot ID changed at every restart.
  - GoDaddy's Hosted Database page says uploaded files and assets persist across deploys, and that re-uploading code or pulling from GitHub never deletes them. That sits uneasily with the one local-disk loss seen in the spike.
  - No backup is documented by GoDaddy for files or the database. Preview apps are removed automatically after 30 days (GoDaddy FAQ). After a plan is canceled, apps, secrets, databases and storage are permanently deleted after 30 days.
  - GoDaddy documents `public/assets` as the folder for files that must persist between deployments; its behavior is not yet separated from the other local paths.
  - Even with `/private` assumed durable, no backup exists for it, so the audio would be a single copy on the host.
- **No websockets in v1.** The API is plain REST. Text is saved when the user leaves the text field; asset processing status is polled by the browser every second or two while an asset is `processing`. Whether the host supports websockets stays unknown and does not matter until co-editing, which is out of scope.
- **One active session per media project.** Opening a media project gives the tab a new session ID, stored on the media project as its current session. Every save carries the session ID, and the server refuses saves from any other session. The older tab learns on its next save (or a light poll), shows "this media project was opened elsewhere", and closes the editor while keeping its unsaved text visible so it can be copied. This works across browsers and devices. Text typed since the last field blur is lost if the browser crashes; the owner accepts this.
- **Uploads** are a single request, with no resumable protocol: if an upload fails, the user restarts it. Verified: bodies up to 100 MiB were accepted on both environments (about 19 s at 5 MiB/s from the owner's machine). The server rejects files over 100 MiB with a clear message. A 5-minute stereo 24-bit 48 kHz WAV is about 86 MB, so it fits; 32-bit float or 96 kHz would not. The 502 returned at 100 MiB plus 1 byte most likely came from our own route cap (the route destroys the connection above 100 MiB), so it does not show a host limit. A cover or a character picture is limited to 10 MB.
- Database backups depend on whether scheduled jobs exist. Unconfirmed.

## 5. Data model

The spine is User → Membership → Media Project → Chapter → Segment → Scene → Cue → Clip → Asset. A segment also has Lanes, and a Media Project has Characters. Users also belong to Teams. All entity IDs are generated by the app (ULID, `CHAR(26)`, collation `ascii_bin`). All times and lengths are integer milliseconds; the interface shows seconds. The Media Project's index is derived from its structure and is not stored.

**Naming.** The root entity is called **Media Project** (formerly Book), so the model can hold an audiobook now and other kinds of work later. In code and the database it is shortened to `project` (table `project`, foreign keys `project_id`). A `type` column (audiobook, textbook, film, series, podcast) is added by an additive migration and chosen when the media project is created (decided 2026-10-20). It decides whether the Script View shows the timeline (audiobook, podcast, film and series do; a textbook does not), and the interface can label levels per type (for example Chapter or Act).

**Script order.** The script order of cues is scene order, then start time, then lane order (the lane that comes first in the segment wins a tie). Nothing is stored for it. Dragging a cue in the timeline never moves another cue; ripple (see Lane rules) happens when a cue's length changes and when a cue is inserted, removed or dragged in the writing panel. Shifting a scene shifts everything inside it because cue starts are relative.

**Cue length and clip playback.**

- A cue's length is a stored property. For a speech cue it follows the text (an estimate with Markdown stripped, syllable count and line breaks, minimum 1 second, at a speaking rate that blends the language default with the rate learned from the media project's own recorded takes) until the author sets it by hand or a clip becomes the chosen one (decided 2026-10-20; the cue carries a length-auto flag). From then on the author owns the length, text edits do not change it, and a "re-estimate" action stays available. A speech cue without text starts at the minimum. The estimate is recalculated when the text is saved (Enter or the check button; see the decision log of 2026-10-21), and the change ripples (see Lane rules). An sfx or music cue has no estimate: its length follows the audio length of its chosen clip (decided 2026-10-20), so it starts at the minimum and takes the clip's length when a clip is chosen, and again when another clip is chosen, while length auto is on; setting the length by hand turns length auto off. A change of length ripples like any other.
- The cue's length decides how much of its clip plays: played length is the cue's length if `loop` is -1, otherwise the smaller of the cue's length and the clip's length × (loop + 1). A longer clip is cut at the cue's end without being changed, so lengthening the cue brings the tail back. A shorter clip ends early or, if `loop` is set, repeats. `loop` is the number of extra repeats: 0 plays once, N plays N+1 times, -1 repeats until the cue ends.
- Fade in applies once, at the start. Fade out is measured back from the end of the played part; with no fade set, the end is a hard cut. Offset plus length must not exceed the media's duration, and fade in plus fade out must not exceed the played length; the app enforces both.
- The playback rule is one function in `src/shared`, used by the browser player and later by the audio compiler.
- A "fit cue to clip" action sets the cue's length to the chosen clip's length.

**Lane rules.** Cues on one lane never overlap: a cue ends at the latest where the next one starts, and gaps are allowed. The interface and the API enforce this; it is not a database constraint (one editor per media project makes that safe). A change of a cue's length ripples (decided 2026-10-20): every cue of the scene that starts at or after the changed cue's old end moves by the change, so gaps are kept, and cues that start earlier stay. The lane rule still wins: a moved cue stops against a cue on its lane that did not move. In the timeline a resize ripples by default and trims instead (the cue is cut where the next begins) when a modifier key is held; the API takes the mode (ripple or trim). Overlap across lanes is the point of the timeline.

**Cue types and lanes (decided 2026-10-20).**

- Every cue has a type (speech, sfx or music) and an optional character (none, the Narrator or any other character). Speech cues carry Markdown spoken text; sfx and music cues carry a one-line description in the same text field. A new cue takes the type and character of the previous cue; the first cue of a segment is speech by the Narrator.
- Lanes are created automatically when a cue needs one in a segment. A speech cue with a character goes on that character's lane (title and colour copied from the character); a speech cue without a character goes on a plain "Speech" lane; sfx cues go on the first free "SFX" lane for their time span ("SFX", "SFX 2" and so on), and music cues likewise on "Music" lanes. Lanes are ordered by first appearance in the segment, and the author can rename, recolour and reorder them in the timeline.
- A lane's colour is the character's default colour at the moment the cue picks the character (the default colour is set in the character's edit view). The author can change a lane's colour in a segment afterwards, for example to separate two characters whose colours are too alike, without changing the character (decided 2026-10-20).
- An automatic lane is deleted when no cue is in it any more. *Proposed:* a lane the author renamed stops being automatic and stays; recolouring does not change this, since it is expected (a lane deleted when empty is recreated later with the character's default colour).
- The writing panel colours each cue with its lane's colour, so characters are colour-coded even where the timeline is hidden (a textbook).
- *Proposed:* no manual lane creation in v1, and dragging a cue to another lane in the timeline is allowed among lanes of the same type, after which the cue takes that lane's character.

**Characters.** A character holds a name, a default colour, a picture (an image asset), a description and its files. Its files live in the library under `characters/{name}`, with free subfolders such as `records`, `songs` or `pictures`. The folder is created with the character and renamed with it. Voice references are added when needed. *Decided 2026-10-20:* characters are listed in creation order (the Narrator is created first), with a (+) at the end to add one, and each character's own menu offers Edit and Remove. A new character takes the first unused colour of the character palette (section 12). Changing a character's default colour asks whether to update its lanes in all segments too (default no); otherwise lanes keep the colour they copied. Every new media project gets a Narrator character, which may be renamed and recoloured but not removed. A character cannot be removed while a cue uses it (or a voice actor is tied to it); the message says where it is used, and a "reassign cues to…" shortcut is skipped for now. Statistics per character (segments, speaking time, words) come later in a panel of their own. *Proposed, not yet confirmed:* the folder name is the sanitized name (up to 30 characters, a number on collision), and the folder stays as an ordinary folder when the character is removed.

**Notes.** A note is Markdown text written on the media project itself, a chapter, a segment, a scene, a cue or an asset in the library, and has a type: comment, reference or task. A note can also be written on a note: the replies form a chain of comments that reads as a chat thread, and a reply is never a reference or a task. Its author is a user, the system (for example the Replace task) or later the LLM. Only a user-kind author edits or deletes a note; system notes cannot be edited or deleted. Any author can check or uncheck a task. A note without replies is deleted outright; a note with replies stays as a tombstone ("deleted") so the thread survives, with its text and ref key cleared. Notes are saved in the snapshot, in `Project.json`, each with its author's user ID (no name or email; decided 2026-10-16). Changes and deletions are visible in the Git history, and a note saved in a snapshot stays there after deletion (the owner accepts this).

**References.** There is no reference entity and no References chapter. A note of type reference carries a `ref_key`, a very short string (a citation-style key such as `Smith20` or `ALB-03`; limit 24 characters) that is also its sort key, and holds the source in its Markdown text. It also has an optional `link` (an `http` or `https` URL checked by the app, shown as an openable link with `rel="noopener noreferrer"`). The References view is generated from the reference notes of the media project and has no timelines. It is sorted alphabetically by ref key, or by appearance, which is derived from where each note's target sits in script order (an asset counts at its first cue) and can be grouped by chapter; notes on the media project itself and on assets that no cue uses form their own groups. A cue's reference is a reference note on that cue. Nothing is stored for the order.

**Tasks.** A note of type task is a to-do that can be checked and unchecked (`done at` and `done by` are set when it is checked). A generated Tasks view lists the tasks grouped by chapter, with open and done filters; the chapter of a task is the chapter of its target, and tasks on the media project itself and on assets form their own groups. Nothing is stored for the grouping. The open-task counter counts task notes with `done_at` empty and not deleted.

**Limits.** The two-digit fields set limits that the API enforces with a clear message: 99 numbered chapters, 26 introductory chapters, 99 segments per chapter, 99 scenes per segment and 99 minutes within a scene.

**Identifiers, ordering and deletes.**

- IDs are ULIDs stored as `CHAR(26)` with `ascii_bin`: generated by the app, time-sortable so inserts cluster well in InnoDB, and readable in the host's database view (which cannot run SQL).
- Ordered siblings (chapters in a media project, segments in a chapter, scenes and lanes in a segment) carry a dense integer `position`, 1 to n, with a unique index on (parent, position). An insert or move renumbers the siblings in one transaction, shifting in descending order (`UPDATE … ORDER BY position DESC`) so the unique index never sees a duplicate; confirmed in the spike (without `ORDER BY` the same statement fails with a duplicate entry), so the fallback is not needed. Folder indexes are derived from the position.
- Delete rules: media project → chapter → segment → scene and lane → cue → clip cascade. A note cascades from its media project, from the chapter, segment, scene, cue or asset it targets, and (as a reply) from its root note; deleting an asset warns about its notes, including references. `clip.asset` and `character.picture` are `RESTRICT`; `lane.character`, `cue.character` and `membership.character` are `RESTRICT`; `cue.clip`, `note.author`, `note.done_by` and `project.cover` are `SET NULL` (the cover rule is proposed). Team rows cascade from `team` to `team_member`, and user rows cascade to `team_member`. Deleting a whole media project is an app routine that removes rows in a fixed order (notes, clips, cues and so on, then assets) instead of relying on one cascade, because `RESTRICT` keys such as clip to asset may fail inside a cascade which the spike confirmed: a one-statement project delete fails on the clip to asset key; before deleting anything it asks the user whether the files on disk (every asset in the library and its derived files) should be deleted too or kept, and then acts on the files as chosen. The database never touches files, so the app collects affected assets and asks the orphan question before deleting rows.
- Renames and reorders run in one transaction that locks the media project row first (`SELECT … FOR UPDATE`). Paths and positions are updated without committing, the files are renamed with every move remembered, any failure undoes the moves in reverse and rolls back, and the commit comes last. A crash in the few milliseconds around the commit leaves files and rows apart, which the reconciler repairs by hash. The lock also stops a second reorder on the same media project while one is running.

**Accounts and login.** The login is the email and a password; there is no public sign-up. Passwords are hashed with Node's built-in `crypto.scrypt` (`src/auth/password.ts`; random salt per user, parameters stored with the hash as `scrypt$N$r$p$salt$hash`, cost N=65536, r=8, p=1, upgraded at the next login if the cost is raised), because native modules such as `argon2` may not build on the host. After login the browser holds one signed (HMAC-SHA256 with `SESSION_SECRET`), `HttpOnly`, `Secure`, `SameSite=Lax` cookie `rs_session` valid for 14 days, holding the user ID, the expiry and a short stamp derived from the user's password hash; there is no session table. Each request loads the user by ID, so a disabled user is locked out at once, and a changed or reset password changes the stamp and ends every older cookie of that user. The login route is rate-limited in memory (8 failures per account and 40 per address in 15 minutes, with an unknown email costing the same scrypt time as a wrong password). `user.last_login_at` is set at each login.

**Account management (no shell on the host).** The admin is the account whose email is `ADMIN_EMAIL`. The first admin is created at startup from `ADMIN_PASSWORD` when no account has that email; its first login must change the password. If the admin is locked out, setting `RESET_ADMIN_PASSWORD` resets the admin password at the next start (and re-enables the account, with a forced change); the variable is removed afterwards, since it resets at every start while it is set. The admin works in the app (`/app`, Accounts screen; API under `/api/admin`): create an account (the server generates a temporary password such as `K7PQ-M2XD-R9TC`, shown once and flagged `must_change_password`), reset a password the same way, disable and enable users, and manage teams and team members. The admin no longer adds, changes or removes project memberships; authors do (see Membership rules). Every user can change their own password. There is no "forgot password" link until outgoing email works; the admin resets it. Other settings: `COOKIE_INSECURE=1` drops `Secure` for plain-http local runs. The screens are plain files in `public/` for now and are replaced by the React app.

**Membership rules.**

- Every non-admin user can create a media project and becomes one of its authors. The API refuses media project creation by the admin account. A new media project gets a Narrator character.
- **Roles (decided 2026-10-16; one role per membership).** There is no owner role: every author is an owner in effect. *Author*: everything, including recording, managing members and roles, and deleting the media project. *Voice actor*: records into cues, and writes comments and tasks, only on the cues whose character is the one they are tied to (the Narrator included); with no character set they cover every cue. *Translator*: not yet decided. *Reviewer*: creates notes of any type (comment, reference, task) and nothing else. *Reader*: reads and listens only. Every role except reader can save a snapshot, because their changes reach the snapshot repo only through one. **Built in v1 (owner, 2026-10-16): only the author role works; every other role is treated as a viewer (read and listen only, no snapshots).** The designs for the other roles wait until they are needed.
- Only authors add, change or remove members and roles (an author may also remove other authors). An author searches by name or email, at least 2 characters, among users who share at least one team with them. The search leaves out disabled users, the admin and current members. A user in no team is standalone: nobody can find them, and they work on their own media projects until the admin puts them in a team.
- Removing a user from a team does not remove their memberships; teams only scope the search.
- Last-author rule: the last author of a media project cannot be removed or demoted, and the admin cannot disable a user who is the last author of any media project until another author is added.
- Members panel behavior (decided 2026-10-20): every member sees the member list (name, email, role); an author may remove or demote themselves unless they are the last author; removing a member takes their access at once and keeps their notes, linked by user ID.
- The admin account cannot be a member of a media project or a team. The admin sees only users and media project overviews (cover, title, members, approximate size), never manuscripts.
- Any author can delete the media project, which runs the ordered delete (decided 2026-10-16). *Proposed:* the author confirms by typing its title.
- *Proposed, not yet confirmed:* the product owner works under a personal non-admin account. Memberships the admin account holds today (test media projects) are transferred to that account before the rule is enforced.

**Infrastructure tables.** `snapshot` records each saved snapshot (a version list in the interface; "dirty since" on the media project is cleared by a snapshot only if nothing changed meanwhile). The asset's `status` (pending, processing, ready, failed) and its claim columns hold the state of encoding, image reduction and peaks work: who claimed it and when, the attempts and the last error; a worker claims a row with a conditional `UPDATE … WHERE status = 'pending'`, since `SKIP LOCKED` is unverified. There is no rename journal. Drizzle keeps its own migrations table.

The unique `(parent, position)` index doubles as the foreign key index.

A thread is flat: every reply points at its root note (one cascade level), and `reply_to_note_id` only records which message a reply answers, so no cascade runs through it. **Write path and snapshots.**

- **Touching the project.** Every write that ends up in a snapshot (structure, cues, clips, notes, assets, characters, project fields) calls one helper at the end of its transaction: `UPDATE project SET revision = revision + 1, last_edited_at = NOW(3), dirty_since = COALESCE(dirty_since, NOW(3))`, plus `UPDATE user SET last_edit_at = NOW(3)` for the acting user. Logins, sessions and snapshot rows do not count. It is app code, not a database trigger, because triggers on the host are unverified.
- **Saving a snapshot.** The function `saveSnapshot` reads the whole project inside one `START TRANSACTION WITH CONSISTENT SNAPSHOT` read-only transaction, so every file comes from one moment, and reads the revision in the same transaction; writers are not blocked. The JSON and Markdown files are generated from memory (deterministically, so an unchanged project produces identical files) and committed to GitHub (inside the GitHub `VersionStore`, this is a commit and a push). After a successful commit it runs `UPDATE project SET dirty_since = NULL WHERE id = ? AND revision = <the revision it read>`; if no row changes, something was written meanwhile and the project stays dirty. The `snapshot` row stores the revision it captured. The editor can use the revision to detect stale saves.
- **Migration order.** Three foreign key cycles exist (project and asset through the cover, cue and clip through the chosen clip, and character with asset through the picture). Drizzle emits every foreign key as a separate `ALTER TABLE ... ADD CONSTRAINT` after all tables are created (confirmed by generating the SQL and by the first migration on the host), so the cycles need no manual ordering. The migration runs from the app under an advisory lock, as decided earlier.
- **Reserved words.** `character` is a reserved word in MySQL, so raw SQL must quote it with backticks (Drizzle always does). `loop` is the other one, already renamed to `loops`.
- **Schema in code.** The Drizzle schema that mirrors these tables is in the repo at `src/db/schema.ts`, with `drizzle-orm` (dependency) and `drizzle-kit` (dev dependency) added and `npm run db:generate` writing migrations to `drizzle/` (config in `drizzle.config.ts`). It type-checks against Drizzle 0.45, and the migrations `0000` to `0022` are generated in `drizzle/`; `0000` and `0001` have run on the host, `0002` to `0022` (2026-10-20 and 2026-10-21) have not yet. Applying them to the host happens by deploying: the app runs pending migrations at startup.

**Origin field.** Every Clip carries an `origin`: `human-recorded`, `generated`, or `voice-converted` (a human performance converted to a character voice). It is unused in v1 but cheap to add now and keeps later claims honest.

**Version manifest.** A saved version is text plus timeline data plus a manifest mapping each asset to its ID, path and hash. Restoring a version restores text, timeline and manifest; audio that has since been renamed or deleted shows the missing-file icon. Audio files themselves are never versioned, only referenced.

**Translations.** A translated cue stores the original's `cueId` and a `sourceHash` of the original text it was translated from. The side-by-side view joins on the ID. If the original later changes, the hash no longer matches and the app flags the translation as out of date.

## 6. Storage, versioning and provenance

The version history exists to show that the text was written gradually, in small increments, by the author. Only text is proven, and v1 keeps it simple.

**Versioning rules**

- Text is saved to MySQL when the user leaves the text field.
- A snapshot is created only by the manual "Save snapshot" action of an author (in v1; later every editing role), with an optional label. There is no autosave to GitHub in v1. Saving a snapshot is a single function (`saveSnapshot`) that takes a media project and an optional label, so a timer can call it later.
- **Recoverability (owner, 2026-10-16):** every media project must be recoverable from the snapshot repo plus the library; only memberships and user accounts need not be. So structure, cues, clips, notes, characters (name, colour, picture, description, folder), project fields (type, title, subtitle, language, cover) and the asset manifest all reach the repo. Notes carry only their author's user ID (decided 2026-10-16: no names or emails in the repo); an import matches the ID to a user when that user still exists, and otherwise the author stays empty. Derived files (MP3 copies, reduced images, peaks) are regenerated from the masters.
- The GitHub API creates the commit directly on the remote, so "commit" and "push" are one step inside the GitHub `VersionStore`. The interface and the rest of the code say "snapshot".
- The app shows a "Changes not in a snapshot yet" indicator with the time since the last snapshot.
- **Accepted risk:** the proof of gradual writing depends on saving snapshots often. A long gap shows up as one large jump in the history. Until a snapshot is saved, the text exists only in MySQL, which has no documented backup.
- The snapshot repo is private (decided 2026-10-16; the public repo and the per-project visibility setting are dropped). A private repo cannot be checked independently by a third party, so the proof of gradual writing is weaker until publishing the history exists (section 7).
- History is append-only: force-push and branch deletion are disabled, and the app never rewrites history.
- Commits are created through the GitHub API (verified). Commit author and committer dates are set by the caller or defaulted by GitHub, so they prove nothing alone, and the commits are unsigned. GitHub's own record of the push or ref update is the independent timestamp; that has not been verified yet.
- Signed commits and an external timestamp (OpenTimestamps or an RFC 3161 authority) are planned additions, not v1.

**Repository layout (owner, 2026-10-16).** The snapshot repo holds one folder per media project. The live state is in MySQL tables; the files below exist only in the repo and are generated from the tables just before each commit:

```text
<repo_folder>/
    Chapters/
        <index> - <title>.md   (one per chapter)
    Project.json
    References.md
    Script.md
    Tasks.md
```

- `Project.json` holds everything needed to reconstruct the media project: project fields (type, title, subtitle, language, cover), characters, the structure (chapters, segments, scenes, lanes), cues with their text, clips (asset ID, path and hash, offset, length, gain, fades, loop, origin), notes (each with its author's user ID, author kind and link) and the asset manifest. IDs are kept, so an import (a later function) can restore identity. It is the source of truth; nothing else in the repo is read back.
- `Chapters/` holds one Markdown file per chapter with that chapter's script, named `{index} - {title}.md` with the library's chapter index (`01`, `00A`) and the title cleaned of characters unsafe in file names (proposed). `Script.md` is the whole script. All of them are generated and written at snapshot time only; a chapter rename renames its file at the next snapshot.
- `References.md` is generated from the reference notes (sorted by ref key: key, link, description, target path). `Tasks.md` is generated from the task notes, grouped by chapter, open tasks before done ones; tasks on the media project and on assets form their own groups. Comments, tasks and references stay out of `Script.md` and the chapter files (decided 2026-10-22), so a note edit or a checked task never changes the text history.
- All files are written deterministically (fixed order, fixed key order, one key per line), so an unchanged project produces identical files and Git records no change.
- Memberships and user accounts are not in the repo (recoverability rule above).
- **Project folder.** The folder is named by `project.repo_folder`: suggested from the title when the media project is created, cleaned of characters unsafe in file names, and unique across all media projects (one repo holds them all; the check ignores case). It does not follow later title changes. Changing it is a separate action in Project View: if a folder with the current name already exists in the repo, the app renames it at once in a commit of its own (file contents unchanged, other unsaved changes not included); otherwise only the field changes. A name that is taken is refused (decided 2026-10-16; the details are proposed).
- Translations will live in a separate language layer that mirrors the structure, never inside the original cues; their place in this layout is decided when the Translation view is built.
- In `Script.md` and the chapter files, the narrator's text appears as plain text with no name in front; a cue by any other character starts with the character's name in bold, a colon and an em dash, such as `**Marta:** — Come in.` (decided 2026-10-22).
- In `Script.md` and the chapter files, an sfx or music cue appears as a marked direction built from its text, such as `[SFX: door slam]` or `[MUSIC: slow strings]` (decided 2026-10-20; the exact markup is proposed).

**What the proof can and cannot show.** A gradual trail shows a writing process. It does not prove that no AI was involved, because text could be pasted in small pieces. Later, typed-versus-pasted tracking and an edit-event log would strengthen it. The LLM feature is note-only by default and does not write into the text, which keeps the trail clean.

**Central account trade-offs.** One central GitHub account (and later a central storage account) is simpler for users, but the operator carries the quota, cost and risk, and other authors' proof depends on trusting that account. In v1 the operator also carries the server's disk quota. The admin sees the titles and covers of every media project, including private ones. Say so clearly in the product.

**Library and assets**

- **One library per media project**, kept as a folder tree on the server's disk behind `BlobStore`. The logical tree in the app is the physical tree: there are no folder rows, folders are directories, and the paths of assets are stored in the database. A later Drive copy mirrors the same tree. A common library shared between media projects is a later idea (another root folder).
- **Free and managed folders.** The author creates and organizes the free folders (for example `songs` or `bird records/peacock`). Two parts are managed by the app: `storyline` and `characters/{name}`. `storyline` cannot be renamed, and neither can the folders under it by hand.
- **Asset record.** Every file has an asset record: ID, path, media kind, size, media info, hash and status. Clips point to the asset by ID (a foreign key, with deletion restricted), never by path, so a rename never touches clips. Assets are never updated; a new version is a new asset.
- **Hash.** The hash is SHA-256 of the audio samples (the data chunk of a WAV), so a move, rename or metadata edit leaves it unchanged; other files hash their bytes. The ID and the hash are separate: the ID is the identity, the hash finds a file again. The hash is unique per media project: no duplicate files, an upload or recording that matches returns the existing asset ("already in the library at …").
- **Derived files** sit beside the master and move with it: the MP3 playback copy of a WAV (same base name, `.mp3`), the reduced copy of an image (`{base}_{W}x{H}.{ext}`, for example `photo_450x600.jpg`) and the waveform peaks. The asset record stores the lightweight copy's path (`lightweight_path`) and size (`size_lightweight`); the library hides exactly the files the database lists as derived and never infers by file name. If a derived name is already taken by another file, the app picks a free name (derived files are app-managed). A missing derived file is regenerated from the master and is not shown as missing. Renaming or moving a master renames its derived file with it.
- **Lightweight copies.**
  - Every WAV is encoded to an MP3, whatever its size. An uploaded MP3 gets no lightweight copy, so its download offers one option.
  - An image whose longest side is above 600 px gets a copy whose longest side is exactly 600 px, keeping the aspect ratio and applying the EXIF orientation. The name carries the real result, so a 3000x4000 photo gives `photo_450x600.jpg`. An image of 600 px or less gets none and `size_lightweight` stays null. The reduced copy keeps the original's image type (a PNG stays a PNG, a JPEG stays a JPEG); decided 2026-10-16.
  - Reduction uses the same `processing` status and worker queue as the MP3 encode, and uses wasm-vips (pure WebAssembly, no native binaries) in a worker thread, verified on the host (section 10).
  - A cover or a character picture is limited to 10 MB. The general 100 MiB upload limit applies elsewhere.
- **Project size.** The approximate size of a media project is the sum of `size` plus the sum of `size_lightweight` over its assets. Peaks and database rows are left out, and the interface labels the figure "approx.".
- **Cover.** The cover is stored at the library root as `cover.{ext}` with the original's extension (`cover.jpg`, `cover.svg`, any); its reduced copy follows the lightweight rule. Setting a new cover opens no collision dialog: the new image becomes the cover, and the previous cover stays in the library as an ordinary asset renamed `cover_{YYYYMMDD-HHmm}.{ext}` (the date and time it stopped being the cover; its derived copy is renamed with it), so earlier covers are kept as versions. Renaming the cover file by hand shows an alert that it is the media project's cover (the link is by asset ID). A replacement in the same minute as the previous one counts as a correction (owner, 2026-10-16: the last version replaces the previous one, since a change that quick means the first replacement was a mistake): the cover of the first replacement is deleted instead of taking a dated name (only if nothing else uses it), so the earlier cover keeps its own dated name. Uploading the current cover again changes nothing, because identical content returns the existing asset. *Proposed:* the time is the server's (UTC), and uploading identical content to an earlier cover swaps the names.
- **Reconciler.** On boot or on demand, the app checks the disk against the asset records. A file with no record is adopted and hashed. A record with no file shows a red "missing" icon on its clips. A missing file whose hash matches a file elsewhere is offered as a relink. A file whose hash no longer matches its record shows an amber "changed" icon. Only files that cannot be placed are hashed, not the whole library on every boot.
- **Renames.** Renaming or moving a folder or file moves the files first and then updates the asset paths in the database (a prefix update for a folder), with a pending-rename record so that a crash in between can be finished or rolled back at boot. Renames happen immediately when an edit commits (the end of a drag, a saved title), not lazily. Snapshots carry each asset's ID, path and hash, so a lost database could be re-linked by scanning the disk and matching hashes.

**Storyline naming.** Dialogue and narration recorded or uploaded in a cue go under `storyline`. Any cue type (speech, sfx or music) can be recorded in place, and the take goes under `storyline` with the same pattern (amended 2026-10-21). Files for sound effects and music can still come from the library.

```text
storyline/{00A..00Z | 01..99} - {chapter}/{01..99} - {segment}/{01..99}.{MMSS} - {lane} - {text} ({n}).ext
```

- Chapter index: `00A` to `00Z` for introductory chapters, `01` to `99` for the others. Segment index and scene index start at `01`, with two digits. Alphabetical order is chronological order.
- `MMSS` is the cue's start within its scene (minutes and seconds). `{n}` is the clip's number among the cue's alternatives, from 1, never renumbered.
- Chapter, segment, lane and the text part are sanitized to plain ASCII (accents transliterated, unsafe characters dropped) and cut to 10 characters; an empty result becomes "untitled". The path is at most about 85 characters.
- If two names still collide, the app replaces the end of the title part with a short ID so the length cap holds. Paths are unique per media project.
- Reordering chapters, segments or scenes, and renaming chapters, segments or lanes, rename the folders and files and update the asset paths. A character rename renames its `characters/{name}` folder; a lane keeps the name it copied.

**Name collisions and Replace**

- On upload, the hash check comes first (identical content returns the existing asset), then the name check.
- If the target path is already used by an asset in a free folder, the app asks: *Replace*, *Save as copy* or *Cancel*. If the path belongs to a derived file, only *Save as copy* and *Cancel* are offered.
- *Save as copy* gives the new file a numbered name (`photo (2).jpg`) and changes nothing else. Apart from this choice, the app never renames a user-uploaded file. The automatic renames are `storyline`, the "(Orphan) " and "(Replaced) " prefixes, the dated names of replaced covers and derived files.
- *Replace*, in one transaction that locks the media project row:
  1. The new file becomes a new asset at the old path (assets stay immutable).
  2. Every clip, the cover and the character picture that used the old asset are re-pointed to the new asset.
  3. Each clip is clamped to the new media's duration (offset and length first, then fades) so the playback invariants hold.
  4. Each affected cue gets a task note "Check fit after replacement", authored by the system (kind `system`, naming the user who replaced the file in its text), one per cue (a note attaches to a cue, not to a clip).
  5. The old asset has no use left. The dialog states this and asks, with *keep* pre-selected: keep it, renamed with the prefix "(Replaced) ", or delete it permanently (the file is removed only after the commit). *Proposed, not yet confirmed.*
- Replace is the only place where a clip's asset changes.

**Names, deleting and orphans**

- A file keeps the name and location given by the first clip that used it. Later clips that use the same file change nothing. Only when that first clip is removed while another clip still uses the file is the file renamed and moved for the next clip (by creation time).
- Deleting a cue or clip asks, for each asset under `storyline` that would be left with no clip, whether to delete it permanently or keep it; the dialog pre-selects keep. Assets outside `storyline` are kept without asking, and library files are never deleted by deleting a cue. Deleting a segment or chapter asks once for the whole batch, with the file count. Only unused alternatives under `storyline` can be deleted by hand.
- Kept files are renamed with "(Orphan) " at the start of the name. If a deleted segment or chapter leaves orphans, its folder gets the same prefix, so its index cannot clash with a new segment at the same position. In the database an orphan is simply an asset with no clip.
- An orphan linked to a new clip is renamed and moved to that clip's path and loses the prefix.
- Deleting is permanent: there is no trash and no backup, and audio is not in the Git history.

**Audio storage and processing.** In v1, files live on the server's disk, behind `BlobStore`, in the library tree above.

- **Upload.** Recordings made in the browser (fragments of dialogue, up to about a minute) and library files (finished songs, up to five minutes) are uploaded as 24-bit WAV, in one request of at most 100 MiB. A failed upload restarts from the beginning. Takes recorded in the browser are the exception for now (decided 2026-10-21): the browser encodes a 128 kbit/s mono MP3 and uploads that, so such an asset has no separate WAV master and no lightweight copy. After the upload the server computes the hash and refuses duplicates.
- **Encoding.** After the WAV master is stored, the server encodes an MP3 playback copy (starting at 128 kbps, adjustable later because the master is kept) with a pure JS or WebAssembly encoder in a worker thread, one job at a time. Heavy work is allowed to run on the web host; the host's CPU and memory limits are untested.
- **Status.** The asset is `processing` until the MP3 exists; the interface shows a loading indicator on the new fragment, and the browser polls the status until it is `ready`. If encoding fails, the WAV is kept, the asset is marked `failed`, and the encode can be retried.
- **Restarts.** There are no scheduled jobs, so job state lives in MySQL. On boot, the app re-queues every asset still `processing`. Preview and Published share the database, so a job needs a claim (who holds it, since when) to avoid two instances encoding the same file.
- **Delivery.** The API answers with a URL for the original and one for the lightweight copy, built from asset ID and variant. Files are streamed through an authenticated route that checks membership each time; a disk path never leaves the server. The player plays the MP3. Cards, lists and previews use the lightweight image; Project View and character profiles load the original image. Downloads: audio offers WAV and MP3 in a menu, an image downloads the original. The app serves audio itself with HTTP range requests so seeking works, and Drive's latency and rate limits do not apply.
- **MP3 start silence.** Encoders add a few milliseconds of silence at the start. The owner accepts this.
- **Storage root.** It must be configurable and sit outside any folder that a deploy replaces. Preview and Published share one root, with no per-environment prefix: they share both `/private` and the database, and the paths stored in the database must resolve from either. Test and live data are mixed on purpose (section 4).

**Backup risk.** Recordings are irreplaceable. Even with `/private` assumed durable, the project has no backup, so before real recordings go in it needs a backup or export routine (see open questions). A Drive `BlobStore` is one candidate, but not the only one.

## 7. Later extensions

Later extensions are planned after the MVP. Each must fit the existing model without reshaping it.

- **Translation view.** Original and translation shown side by side in the Redaction View, paired cue to cue. Translations live in their own language layer in the repo and are paired by the original cue's stable ID, with a source hash to flag outdated translations.
- **Integrated LLM.** A chat for discussing the text and leaving notes. Note-only by default, so it never writes into the manuscript. Any LLM-inserted text would be flagged. LLM notes are saved like any note, with the LLM as author.
- **Speech generation.** Text-to-speech to generate speeches, or speech-to-speech that takes the author's own interpretation and replaces it with a character's voice. Current tools in use: Chatterbox (via Voicebox) for voice cloning and RVC (via Applio) for conversion. Free and open source is a hard constraint. These tools need hardware and software the host does not offer, so this most likely runs as a separate service behind an interface, and the output is a clip with the matching `origin`.
- **Audio compiler.** Renders a segment's timeline into a single audio file, using the shared clip playback rule. Needs ffmpeg or equivalent, which the host does not provide, so where it runs is to be decided.
- **Appendixes.** An ordered list of items with text and an audio file, with no lanes and no timeline. Parked for now; whether an item is a cue without placement or its own small entity, and where its recordings are stored, is to be decided.
- **Video.** A clip can be audio or video, and the asset already records its media kind. Fades stay audio-only. The rule that all clips of a cue share one media kind is placed when video begins.
- **Common library.** A library shared between media projects, as another root folder.
- **Publishing the history.** An explicit action that makes a media project's snapshot history public, with its own repo or visibility setting. Dropped from v1 on 2026-10-16; the `project.visibility` column stays unused until a migration removes it.
- **Script PDF.** A printable `Script.pdf` written beside `Script.md` in the snapshot repo. Parked on 2026-10-16: not needed even for the MVP. It needs a pure JS or WebAssembly PDF generator (no native binaries) with fonts for accented text, and each PDF adds binary size to the repo at every snapshot.
- **Google Drive storage.** A `DriveBlobStore` behind `BlobStore`, one folder per media project, via a central service account; the library tree is mirrored to Drive. Candidate uses are a backup target or an offload of the server disk. Points to settle first (not yet verified against current Google docs):
  - As far as we know, service accounts have no storage quota of their own, so uploads into a folder shared from a personal Google account can fail even though listing works.
  - A Shared Drive avoids this but may require Google Workspace.
  - Whether the owner's account is personal or Workspace decides the route.
  - The spike for this adapter must include a real upload, not only a folder listing.
  - Uploads could go from the browser straight to Drive with a short-lived token, but playback should not stream straight from Drive (latency, rate limits), so a server-side cache or compressed working copies would be needed.

## 12. Visual identity

Status: draft v1 (2026-10-15), agreed in the UI/UX Design chat. The look is a very dark interface with panels in dark brown-toned grays, yolk-yellow highlights like a blackbird's beak, and light green and orange as accents. The base colors come from a photo of a blackbird (palette made with Adobe Color). Lane and character colors are a separate palette of 29 entries (see the open points).

**Reference page.** `docs/blackbird-palette.html` is a self-contained page (open it in a browser) with the swatches, their values and contrast, the proportions, a mock Redaction View with a "show color roles" view, component states and a contrast matrix. **Principles**

- Colors are named by role (design tokens), never used as raw hex values in components, so a later light theme is a change of the token layer.
- Roughly 60% background, 30% panels and supporting surfaces, 10% accents; yolk leads.
- Text pairs meet WCAG AA (4.5:1 for normal text, 3:1 for large text and UI parts), except the muted text, which is for disabled and decorative use only.
- Color never carries meaning alone: alerts and errors also carry an icon and a label.

**Role mapping (proposal, not yet confirmed).** The palette values are agreed; how they map onto the interface was shown in the reference page and is still open to change.

- `primary`: the one main action per screen, the active segment, the selection outline, the playhead and the open-task tag.
- `accent-green`: success and ready, the played part of a waveform, done tasks and reference notes.
- `alert` and `alert-text`: attention, such as a changed file and the "Changes not in a snapshot yet" indicator, which stays calm at first and turns `alert-text` as the gap grows (thresholds not decided).
- `danger`: errors, destructive actions and recording.
- Comment notes use `text-secondary`; the type is told apart by tag label as well as color.

## 13. MVP views

Status (2026-10-20): Projects Collection, Project View and Accounts are settled, and the Script View layout, the cue block, the Story Index, the scenes and the Characters tab are decided (audio details and the Notes, Tasks and References panels are still to be discussed; the Library tab and pictures are built, see the decision log of 2026-10-21). The other views are still to be discussed one by one: Characters, Versions, the Library sidebar, the Notes panel and project export as ZIP. The overall plan is six views (Projects Collection, Project View, Script View, Characters, Versions, Accounts), the Library as a sidebar, Notes as a panel, and ZIP export as an action in Project View; this list is not yet confirmed as a decision.

**Projects Collection (home, for every non-admin user)**

- Lists the media projects the user is a member of, sorted by last edit by default, with sort by title or created and a title filter. An empty state invites the first project.
- Each card shows: the cover (lightweight copy; a placeholder if there is none), title, subtitle, role badge, created, last edit (`project.last_edited_at`), last snapshot (latest `snapshot.created_at`), number of chapters, approximate size (section 6) and three counters: comments, references and open tasks. When `dirty since` is set, it also shows "Changes not in a snapshot yet" with the time since.
- Counters (decided 2026-10-22): comments are root comment notes (a thread counts once; a tombstoned root with replies still counts; replies are not counted); references are reference notes that are not tombstones; open tasks are task notes with `done_at` empty and not deleted.
- "New project" asks for a type, a title, an optional subtitle and a language; it creates the media project, the author membership and the Narrator character, plus Chapter 1, Segment 1, one scene and one empty cue by the Narrator, so writing can start at once.
- Deleting a media project is in Project View, not here.

**Project View (every member; editing by authors)**

- Layout (revised 2026-10-21): one panel with the cover at its left (the reduced copy; Replace and Remove buttons appear on hover, and the cover is stored as described in section 6) and, to its right, the title in a large font, the subtitle below it, then the properties (type, language drop-down showing each language's flag and name (EN-US, PT-BR, DE-DE for now), chapters, size, last edit, last snapshot with the unsaved-changes mark, repository folder) and the **Open script** button at the bottom. There is no "Details" heading. Each language has a profile in code (`src/shared`) with its estimation values, such as `ms_per_syllable`. There is no visibility setting.
- Snapshot repo folder: shown with a "Rename folder" action, separate from the title (section 6).
- Status: created, last edit, last snapshot, chapters, approximate size, the comments, references and open tasks counters (as on the card), and the "Changes not in a snapshot yet" indicator with the **Save snapshot** button and an optional label (authors only in v1).
- Members panel (decided 2026-10-20): a list of the members with name, email, role (Author or Viewer) and the date they were added (`membership.created_at`). Every member sees it; only authors can change a role or remove a member. *Add member*: a search field (2 characters or more) over name and email among users who share a team with the author; each result shows name and email; the author picks Author or Viewer and adds. When nothing is found, the panel says that only users who share a team can be found and that the admin manages teams. Removing a member takes their access at once and keeps their notes (linked by user ID). An author may remove themselves or demote themselves to Viewer, after a confirmation, unless they are the last author (the panel says so). The role menu offers only Author and Viewer in v1.
- Delete media project (authors): the ordered delete, which first asks whether the files on disk are deleted too or kept.
- Export as ZIP: parked until the end of the MVP, because it depends on structures not yet decided.

**Script View (the Redaction View; layout decided 2026-10-20, details still to be discussed)**

- Top bar: the logo and the media project's name on the left (the name opens Project View); on the right the "Changes not in a snapshot yet" indicator with the **Save snapshot** button (authors) and the user menu.
- Four panels. *Story Index* (left): a tree of chapters and segments (details below); clicking a segment opens it in the writing panel. *Writing panel* (center): the open segment as scenes that hold editable cue blocks, with tools to add or remove a scene or a cue. There is no cue dialog: a cue is edited in place (see the cue block below). *Right panel*: tabs for Library, Characters, Notes (Tasks and References are type filters in the Notes tab's header, not separate tabs; decided 2026-10-22). The Notes tab is a tree of Chapter → Segment → Scene → Cue in script order, each level expandable and collapsible (remembered in the browser) and showing its own notes, opening on the current position; notes on the media project and on assets sit in a separate group below. Its header filters by type and searches text, replies included. It does not add notes: a dialog does (see the decision log of 2026-10-22). *Timeline* (bottom, across the three panels): the open segment as lanes over time, shown only for audiobooks, podcasts, films and series.
- A Library file row shows a badge at its left with the number of notes on that asset, coloured by the most urgent type (open task, then reference, then comment); clicking it opens the Notes tab on that asset (decided 2026-10-22).
- One segment is open at a time, with previous and next buttons. Selecting a cue in the writing panel or in the timeline highlights it in the other; during playback the cue under the playhead follows along in the text.
- **Story Index (decided 2026-10-20).** Each chapter row shows its number without padding (`1`, `12`; `A` for an introductory chapter, whose folder index is `00A`) in a column two digits wide, so one-digit numbers leave a little more space before the title, and each segment row shows its position in the chapter the same way. There are no expand arrows: clicking a chapter row expands or collapses it (remembered in the browser). The open segment is highlighted. A (+) at the end of the tree adds a chapter; the new item appears with its title in edit mode, and titles are edited inline. When the pointer is on a row, a "⋯" button appears at its right (always visible on the selected row on touch) and opens that item's menu. Chapter menu: Rename, Add segment, Mark as introductory, Move up, Move down, Delete. Segment menu: Rename, Move up, Move down, Delete. Chapters reorder by drag and drop, and segments can move to another chapter; introductory chapters stay above the numbered ones. Deleting asks for confirmation with counts (segments, cues, notes) and, when clips exist, the keep-or-delete question for the files. A media project may have no chapters and a segment no cues (each then shows a (+)). The open chapter's and segment's titles appear as headings above the writing panel and can be edited there too.
- **Scenes (decided 2026-10-20).** Scenes are visible in every media project type: a textbook is not treated differently, which keeps the implementation simple (the length column on a cue stays too and reads as a reading-time estimate; only the timeline panel is hidden). Each scene is a block whose header row shows its optional title (stored in `scene.label`; added or edited with "Add title" / "Edit title" in the scene's "⋯" menu, nothing is shown while it is empty; a new scene starts titled "Scene " plus its number, so the third scene is "Scene 3", and the author may change or clear it), a thin divider line, then its start (`mm:ss`, in the muted header font) and its duration as "N min M s" (`M s` under a minute, for example `1 min 5 s` or `45 s`; white and bold) at the right of the start, and the "⋯" button. The start and the duration are derived, not stored (decided 2026-10-21). The bar between two cues has a second action, "Split scene here", which moves the cues below into a new scene. A scene's menu offers "Merge with previous" (keeps the cues) and "Delete" (removes its cues, after a confirmation). A segment always has at least one scene.
- **Characters tab (decided 2026-10-20).** A list of the characters in creation order (picture, colour dot, name) with a (+) at the end; a character's menu has Edit and Remove, and a double click on a character opens its edit dialog (decided 2026-10-21). The character dialog has the name, the default colour (the palette of 29 plus a custom picker), the picture (a minimal image upload, 10 MB limit) and an optional Markdown description. The rules are in section 5, Characters.
- **Cue block (decided 2026-10-20).** A left column in the lane's colour shows the length (and the start, read-only) on top, with small icons below it: a circle for the cue type, a clip icon and a notes icon. To the right is the text, edited by double-clicking it (a one-line description for sfx and music), with a character chip beside it. Menus open on click; hover shows only a tooltip.
  - *Type circle:* a menu with speech, sfx and music; the circle shows the type and the lane's colour.
  - *Character chip:* a menu with None, the Narrator, every character, each name written in its default colour (the Narrator's black shows in the normal text colour), and "New character…", which opens the character dialog (name, default colour, picture, description). Picking a character moves the cue to that character's lane, coloured as described under Cue types and lanes.
  - *Clip icon (replaced on 2026-10-21 by the audio menu in the decision log; the text below is the earlier design):* a menu with the chosen clip at the top (its library path), a separator, then Upload, Select from Library and Record, a separator, and all takes to choose from directly. Each take shows its number, origin and length, a play button for auditioning and, on hover, a delete button, which asks the existing keep-or-delete question. There is no "rejected take" state. The icon is dimmed with no clip, shows a spinner while the asset is processing, amber when the file changed and red when it is missing.
  - *Notes icons (revised 2026-10-22):* under the cue's type and character, left of the "now" label, the cue shows what notes it has: a chat balloon for comments, a checkbox for tasks (yellow while one is open, gray when all are done), and a green link icon for references (whether or not the link is filled in); each opens the Notes tab at the cue. The add-note icon (a solid yolk circle with a black plus) appears only while the pointer is on the cue, and opens the dialog that adds a note on the cue. There is no counter beside the audio icon.
  - *Length:* click the length to type a value, which turns length auto off; a small "auto" mark shows while it follows the text or clip. Its menu offers "re-estimate" (speech cues) and "fit to clip". The start is derived from order and ripple and is read-only here; deliberate gaps are made in the timeline.
  - *Resize offer:* when a clip is chosen for a speech cue and its length differs from the cue's, an inline strip on the cue offers "Resize cue to clip" or "Keep" (no dialog). Sfx and music cues follow the clip automatically.
  - Offset, gain, fades and loops (every audio property of a clip) are edited in the timeline only, where a clip appears as a region; they do not exist for textbooks, which have no timeline. For v1 the timeline offers offset (trim) and gain; fades and loops stay stored without an interface.
- Adding and ordering: when the pointer passes the space between two cues, a bar appears with a (+) button at its center; clicking it inserts a cue there (its start is the end of the cue above, and the following cues ripple by its length). The same bar appears under the last cue. Cues are reordered by drag and drop (the dragged cue is placed after the cue it lands on and the rest ripple); dropping into another scene moves the cue there. Changing a cue's length ripples (section 5, Lane rules).
- Readers see the same screen without editing (in v1, every non-author).
- **First working version (owner, 2026-10-20):** everything except audio, and except the Notes, Tasks and References panels, which wait for a later iteration. That means login, Projects Collection, Project View, Story Index, writing panel with cues and scenes, characters and Save snapshot.
- Build order for the earliest use: (1) the Story Index and the writing panel with text only; (2) cue properties, library, clips and playback, with a read-only timeline; (3) recording in the browser; (4) timeline drag and resize.

**Accounts (admin only; the admin lands here and has no Projects Collection)**

- Users: name, email, teams, last login, last edit, media projects with roles, and status. Actions: create (temporary password shown once), reset password, disable or enable, and edit teams. A user may have no team.
- Teams: create, rename, delete (members lose the team, not their memberships) and assign users.
- Media projects overview, read-only: cover, title, members and approximate size. No access to manuscripts, and the admin cannot join a media project.
